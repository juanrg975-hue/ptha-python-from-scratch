Data provenance: what comes from where

With --ptha false and the default --convergence bird, every number in steps 1 to 7, 7b and 9 is derived from public sources: SLAB, Bird (2003), GCMT, and Berryman et al. (2015). PTHA18's own files are read nowhere in that path. The one PTHA18 input you can opt into is --convergence bird-griffin, which makes step 3 read PTHA18's own plate-boundary table (a copy shipped in data/bird/, see below). The only place PTHA18 is read at all is step 8, the optional official run built purely for comparison, and step 9 shows that comparison only from step 8's own output, never by reading PTHA18 directly. This page states that claim precisely and shows how it was checked, not just how it is meant to work.

The one opt-in PTHA18 input: the Bird+Griffin table

data/bird/bird_griffin_traces_table.csv.zip is a byte-identical copy of rptha's DATA/BIRD_PLATE_BOUNDARIES/sourcezone_traces_table_merged.csv.zip: the plate-boundary table PTHA18 itself used. It merges 1060 of Bird's steps that PTHA18 kept, 2645 source-zone traces with plate rates put together by Jonathan Griffin (eastern Indonesia, New Guinea and others) and 100 rows added by Gareth Davies. So it is PTHA18's work, published openly with rptha (BSD-3), not an independent public dataset like Bird (2003).

It is copied into data/bird/ so that no step has to open the rptha/ folder, which is why the audit below sees no rptha/ read. Being a copy does not change where it comes from: a run with --convergence bird-griffin uses a PTHA18 input in step 3. The default, --convergence bird, does not, and gives the same convergence wherever PTHA18 itself used Bird's steps (zone by zone). Step 8 always uses the Bird+Griffin table, since it reproduces PTHA18's own run.

Checked from zero, not just read from the code

Reading the code shows the intent; running it shows the fact. A file-open hook (a Python sys.addaudithook, loaded by every process including subprocesses) was pointed at the three folders that hold anything of PTHA18 or rptha (rptha/, official_ptha_data/, inputs/), and at every connection to NCI. Then a zone PTHA18 never modelled (calabria2, so no cached PTHA18 file for it exists anywhere in the package to begin with) was generated from nothing and run end to end, steps 1 through 9, without --skip-official:

.venv/Scripts/python.exe from_scratch_v12/generate.py calabria --zone calabria2 --folder _audit_test --ptha false --discretizer optimal --convergence bird
.venv/Scripts/python.exe _audit_test/steps/step_total.py --skip-hs

The complete log of every file the run opened inside those three folders:

fetch_official_inputs.py	calabria2	open .../rptha/r/examples/austptha_template/data/sourcezone_parameters/sourcezone_parameters.csv

One line, and it is step 8's. step_total.py tried step 8 (it was not skipped), which launched official_ptha_data/fetch_official_inputs.py calabria2, which opened rptha's zone table to look calabria2 up, found nothing (since PTHA18 never modelled it), and step 8 failed cleanly. step_total.py reported that and moved straight on to step 9, which built a complete report from steps 1-7 alone:

step8_official.py failed (exit 1) -- this step is optional (needs R + rptha, and needs this zone to be one PTHA18 modelled), so continuing to the next step. The final report will be complete for steps 1-7, just without an official-run comparison.
  ...
  note: no official run found at .../outputs_official
  the report will cover steps 1-7 only, with no comparison section. Run step8_official.py first for the full report.
  ...
Steps 1-7 and 9 complete (step 8 skipped).

Zero opens from steps 1 through 7, 7b or 9. The single hit traces to the one process that is meant to touch PTHA18, doing exactly what it is meant to do.

The hook did not watch runs/, where step 8 writes its engine output. A later code review found that step 6 read that folder's summary, when step 8 had already run, to quote PTHA18's convergence in the input JSON's text note. It is now behind USE_PTHA like the other two (below); on calabria2 it could not have fired, since step 8 found no PTHA18 zone to run.

Checked again on v9, on a zone PTHA18 did model

calabria2 proves that nothing is read when there is nothing to read. The harder case is a zone whose PTHA18 files are in the package, run with the most v9 machinery: kermadectonga2, segmented (Berryman's segment end points, per-segment GCMT and Berryman rows), generated from nothing and run through steps 1 to 7 and 9 (step 8, the comparison, skipped). The same kind of hook watched every open of rptha/, official_ptha_data/, the package-root inputs/, validation/ptha18_reference/, any sourcezone_parameters, *_official.json, outputs_official, runs/python/kermadectonga2_official* and ReportPTHA, and every request to NCI:

.venv/Scripts/python.exe from_scratch_v12/generate.py kermadec --zone kermadectonga2 --folder _audit_seg --ptha false --segmented true
.venv/Scripts/python.exe _audit_seg/steps/step_total.py --skip-official --skip-hs
(empty: zero opens, zero NCI requests)

To be sure the hook was live in every subprocess, the same hook with one public file added to its list (Bird's PB2002_steps.dat.txt.zip) logged step 3's read of it. The run's results equal kermadectonga2_v9seg's to the last digit (25 tables). Step 7b, run on the same folder afterwards, opens nothing either. (2026-09-30.)

One latent path remains, and now says so: an input JSON without events.scaling_relation and shear_modulus_Pa makes the engine and step 7b read them from PTHA18's sourcezone_parameters.csv, which is what an official input needs. Step 6 always writes both, so a from-scratch run never takes it; if it ever does, the log prints a note.

Why steps 2, 5 and 6 could read PTHA18, and why they do not

Three steps have a code path that can read an official file, for the --ptha true case (comparing your run's mesh, GCMT count or convergence against PTHA18's while building it). Both are behind an explicit guard on USE_PTHA, which generate.py --ptha false sets to False:

StepWhat it could readThe guard
2official_area_and_dip(): PTHA18's published mesh area and dip, for the printed comparison tableoff = official_area_and_dip(...) if USE_PTHA else None, and the fallback branch is elif USE_PTHA:, so with USE_PTHA = False neither branch ever calls it
5read_official_gcmt_count(): PTHA18's own selected-event count for this zone, from step 8's extractionoff_count, off_duration = read_official_gcmt_count() if USE_PTHA else (None, None)
6read_official_convergence(): PTHA18's convergence from step 8's engine run (runs/python/<zone>_official/logic_tree_summary.csv), only quoted in the input JSON's provenance note, never used in a numberofficial_convergence = read_official_convergence() if USE_PTHA else None

All three functions also start with if not os.path.exists(...): return None, so even reached with USE_PTHA true they degrade to "not available" rather than fail when step 8 has not run. With --ptha false the guard above stops them being called at all.

Step 9's report: the comparison without the read

The report can show a from-scratch-vs-PTHA18 comparison (mesh maps, convergence, GCMT count, rate curves) without step 9 ever opening a PTHA18 file itself. Every "official" path it reads resolves under this example's own folder:

Constant in step 9Resolves to
OFFICIAL_RUN_DIR<folder>/outputs_official/
REFERENCE_DIR<folder>/outputs_official/ptha18_reference/
OFFICIAL_NC, OFFICIAL_CONV_NPY, OFFICIAL_GRID_NPY, OFFICIAL_GCMT_JSONall inside REFERENCE_DIR

Those files exist only if step 8 wrote them. Without step 8, every os.path.exists(...) guard around them is false, the report says so in plain words, and steps 1-7's own numbers are shown in full: a from-scratch run is a complete result on its own, not a stub waiting on PTHA18.

Where step 8 itself fitsStep 8 is documented on its own page: 8. The official PTHA18 run. It is the one place this package reads PTHA18, by design, since a comparison needs something to compare against, and everything it reads and writes is listed there.
