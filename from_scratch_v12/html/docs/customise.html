Your own runs

Change a setting, re-run

Every example folder is yours to change. Each setting lives in exactly one place: a constant at the top of one step script, a key of the input JSON, or a flag of generate.py. Change it there, then re-run that step and every step after it. This page says where each setting lives, what to re-run, and shows two real cases.

At a glance: what to re-run

The one trapRe-running step_total.py on a folder whose input JSON already exists keeps that JSON (step 6 prints already exists -- NOT overwriting it). That protects your hand edits, but it also means a change made in steps 1 to 5 never reaches the rates until you run step6_write_input.py --force.

Example 1: cells 35 km wide

PTHA18 used 35 km wide cells on puysegur2 and 50 km elsewhere. There are two ways to change the width of an existing folder.

quick In the input JSON

  1. In inputs/input_puysegur2_scratch.json, set "desired_unit_source_width": 35.0.
  2. Run step 7, then step 9 (or step_total.py: step 6 will keep your file).

The engine sees that its geometry no longer matches step 2's saved mesh, prints step 2's saved grid does not match ... rebuilding, and meshes at 35 km. Steps 3 and 5 still used step 2's mesh: exact when the columns do not change (the width only changes rows), approximate otherwise.

exact At the source, step 2

  1. In steps/step2_build_grid.py, set DESIRED_WIDTH_KM = 35.0.
  2. Run steps 2, 3, 5, then step6_write_input.py --force, then 7 and 9.

Every step then uses the 35 km mesh. Step 6 copies the width from step 2 into the JSON, so the engine reuses step 2's mesh (mesh: reusing step 2's grid).

.venv/Scripts/python.exe puysegur2_v9/steps/step2_build_grid.py
.venv/Scripts/python.exe puysegur2_v9/steps/step3_convergence.py
.venv/Scripts/python.exe puysegur2_v9/steps/step5_subset_gcmt.py
.venv/Scripts/python.exe puysegur2_v9/steps/step6_write_input.py --force
.venv/Scripts/python.exe puysegur2_v9/steps/step7_run.py
.venv/Scripts/python.exe puysegur2_v9/steps/step9_report.py

What changes, on real data

The width sets the number of rows through rptha's rule (rows and width). Measured with the exact route on a copy of kermadectonga2_v8, before v9 changed the zone's Berryman values (so the rates are v8's, 0.2200 rather than v9's 0.2251; the comparison between the two widths is what matters here):

kermadectonga2cellsarea, km2mean dipconvergencescenariosedge multiplierrate Mw 7.2+ / 8.0+
width 50 km (the example)73 x 3 = 219542,55915.42°99.363,0756.140.2200 / 0.0379
width 35 km73 x 4 = 292542,79215.41°99.373,5135.900.2200 / 0.0379

One more row of smaller cells, 438 more scenarios, the same fault surface (area within 0.05%), and practically the same rates: the moment balance depends on the area, the dip and the convergence, which the width does not change.

puysegur2 is a special caseIts zone is only about 71 km wide down the slope. With 50 km, rptha's rule gives 1 row and the minimum of 2 rows applies; with 35 km the rule itself gives 2 rows. Both give the same 13 x 2 mesh, with cells about 35 km wide, so on puysegur2 the width setting does not change anything.

Example 2: a fixed convergence of 35 mm/yr

PTHA18 used a constant 35 mm/yr on puysegur2 instead of Bird's model (25.60 mm/yr on this mesh). Changing only the number is not enough, because the Bird model has three parts:

Part of the modelBird (default here)Constant (PTHA18 on puysegur)
rate for the moment balancearea-weighted Bird convergencethe constant
how scenarios of one magnitude share its rateconvergent_slip_weighted + convergent_slip_profileinverse_slip, no profile
LEVEL 4 target shapeconvergence_profile (Bird's div per column)flat

right Step 3's override

  1. In steps/step3_convergence.py, set CONVERGENCE_OVERRIDE_MM_PER_YR = 35.
  2. Run step 3, step6_write_input.py --force, 7, 9.

Step 3 writes 35 and marks the zone as constant-convergence; step 6 then writes inverse_slip and no profiles: PTHA18's model.

mixed Only the JSON number

Setting "tectonic_convergence_mm_per_yr": 35 and re-running step 7 changes the moment balance only: the scenarios are still shared by Bird's convergent slip and LEVEL 4 still aims at Bird's shape. To get PTHA18's model from the JSON alone, also set "conditional_probability_model": "inverse_slip" and delete the two ..._profile keys.

Always the horizontal rateWhatever you type is the horizontal plate rate. The engine divides it by cos(mean dip) itself; typing v / cos(dip) would apply the correction twice (why).

Other common changes

Force the number of rows

Set N_DOWNDIP_OVERRIDE = 3 in step 2 and re-run 2, 3, 5, 6 --force, 7, 9; or set "n_downdip": 3 in the JSON and re-run 7 and 9. The override replaces rptha's width rule entirely.

Compare optimal with lm or mid on the same zone

The cleanest way is a second folder: generate.py kermadec --zone kermadectonga2 --folder kt2_lm --ptha false --discretizer lm, then step_total.py. Each folder downloads its own SLAB raster (into data/slab1/ or data/slab2/) and GCMT files (into data/gcmt/); to skip the second SLAB download, copy the .grd from the first folder, or put it once in from_scratch_v12/data/slab2/ (or slab1/), which every folder checks. PTHA18's files are shared. In an existing folder, set "discretizer": "lm" in the JSON and re-run 7 and 9.

Use PTHA18's width and row count (--ptha true)

Generate a new folder with --ptha true. Step 2 then uses PTHA18's width for the zone and, when PTHA18's cell table is available, its row count; step 6 uses PTHA18's scaling row. The Bird table is a separate flag, --convergence bird-griffin (when it matters). The contours are the same as with --ptha false. On a zone PTHA18 never modelled, use --ptha false. What each step reads in each mode: the list.

Other literature values (coupling, b-value, Mw_max)

For one folder: edit rates.coupling.spreadsheet_values, rates.b_anchor or rates.mw_max_observed in the JSON and re-run 7 and 9. For every future folder of a zone: edit its row in lib/berryman_params.py.

A different earthquake window, or no Bayesian update

Change WINDOW_START / WINDOW_END in steps 4, 5 and 6 (each has its own copy), then re-run 4, 5, 6 --force, 7, 9; step 6 computes the duration from its copy. To see the rates without the update, set "update_logic_tree_weights_with_data": false in the JSON.

Start again from the data

Delete inputs/input_<zone>_scratch.json (or run step 6 with --force) and run step_total.py: every step then rebuilds from its inputs. Downloads (the folder's SLAB raster and GCMT files, PTHA18's files) are kept and not repeated.

Check that a change took effect

  • Mesh: step 2's and step 7's log lines grid: ... unit sources and mesh: reusing step 2's grid (or rebuilding); the report's STEP 2 cards.
  • Input: the report's step cards show the values the engine used; the JSON's _..._provenance notes say where each came from.
  • Rates: outputs/logic_tree_summary.csv (mean dip, convergence, edge multiplier, TVD) and outputs/rate_curves.csv.
The 35 km example was run on a temporary copy of kermadectonga2_v8 (steps 2, 3, 5, 6 --force and 7), so the example folder itself is unchanged.
